# Бэкенд сервиса черновиков объявлений

Spring Boot API принимает исходное объявление, запускает анализ через внешний ML-сервис и хранит предложенные черновики для просмотра и редактирования. PostgreSQL и бэкенд запускаются отдельными контейнерами. Сам ML-сервис в этом репозитории пока отсутствует.

## Запуск

Нужен Docker Desktop с работающим Docker Engine. В `backend/.env` задайте как минимум `DB_PASSWORD` и `JWT_SECRET` (секрет JWT — не короче 32 байт). Файл `.env` не включается в Docker-образ. Опционально можно задать `CORS_ORIGINS` и `ML_BASE_URL`.

```powershell
cd backend
docker compose up -d --build
docker compose ps
docker compose logs -f backend
```

API доступно по `http://localhost:8080`, PostgreSQL — на порту `5432`. Внутри Compose бэкенд подключается к `postgres:5432` с пользователем `avito` и паролем из `DB_PASSWORD`. При повторном запуске данные БД сохраняются в томе `avito_pgdata`. Для остановки без удаления данных: `docker compose down`.

При первом запуске обновлённой версии из существующей таблицы `users` удаляются старые столбцы `middle_name`, `birth_date` и `phone` вместе с их данными. Если эти данные нужны, сделайте резервную копию БД до обновления контейнера.

`ML_BASE_URL` в Compose по умолчанию равен `http://host.docker.internal:8000`: этот адрес подходит для ML-сервиса, запущенного на хосте с Docker Desktop. Бэкенд отправляет ему `POST /internal/v1/avito/drafts`; пока сервиса нет, анализ завершится ошибкой `ML_UNAVAILABLE`. Если ML будет в другом контейнере, укажите его сетевое имя и порт через `ML_BASE_URL`.

## Общие правила API

- Все пути ниже начинаются с `http://localhost:8080/api/v1`.
- Для JSON-запросов передавайте `Content-Type: application/json`.
- Кроме регистрации, входа, обновления токена, выхода и каталога, требуется заголовок `Authorization: Bearer <accessToken>`.
- `{id}` в URL — UUID соответствующего объявления, анализа или черновика. Пользователь видит только собственные данные; чужой или отсутствующий объект возвращает `404`.
- `mcId` — число от 101 до 106. Имена микрокатегорий находятся в `backend/src/main/resources/application.yaml` и доступны через каталог.
- При ошибке API обычно возвращает `{"error":{"code":"...","message":"...","details":{},"requestId":"..."}}`. Ошибки валидации тела дают `400`, конфликт email — `409`, отсутствие или недействительность access token — `401`.
- В `application.yaml` включено исключение полей со значением `null` из JSON. Поэтому некоторые необязательные поля могут отсутствовать в ответе. В `GET /analyses/{id}` поля `title` и `text` внутри `result.drafts` сохраняют явный `null`.

## Авторизация и профиль

### `POST /auth/register`

Регистрирует пользователя и сразу выдаёт пару токенов. Доступен без авторизации. `firstName` и `lastName` обязательны, до 100 символов каждый; `email` — корректный адрес до 255 символов; `password` — 8–72 символа.

```json
{"firstName":"Иван","lastName":"Иванов","email":"ivan@example.com","password":"password123"}
```

Ответ `201` имеет формат:

```json
{"accessToken":"<jwt>","refreshToken":"<token>","tokenType":"Bearer","expiresIn":900,"user":{"id":"<uuid>","firstName":"Иван","lastName":"Иванов","email":"ivan@example.com","role":"USER"}}
```

`expiresIn` измеряется в секундах; текущая настройка access token — 15 минут. Повторный email даёт `409`.

### `POST /auth/login`

Проверяет учётные данные и возвращает такой же ответ с новой парой токенов (`200`). Доступен без авторизации.

```json
{"email":"ivan@example.com","password":"password123"}
```

Неверные данные дают `401` с кодом `INVALID_CREDENTIALS`.

### `POST /auth/refresh`

Меняет действующий refresh token на новую пару токенов (`200`); старый refresh token отзывается. Доступен без access token.

```json
{"refreshToken":"<token>"}
```

Ответ имеет тот же формат, что при входе. Недействительный, истёкший или уже отозванный refresh token даёт `401`.

### `POST /auth/logout`

Отзывает переданный refresh token. Доступен без access token.

```json
{"refreshToken":"<token>"}
```

Ответ `204` без тела. Если токен не найден, метод также возвращает `204`. Уже выданный access token этим запросом немедленно не отзывается: он действителен до истечения срока.

### `GET /auth/me`

Возвращает профиль текущего пользователя (`200`). Тела запроса нет; нужен access token. Формат — объект `user` из ответа регистрации, без внешней обёртки.

### `PUT /auth/me`

Обновляет профиль текущего пользователя (`200`). Тело содержит `firstName`, `lastName` и `email`; пароль этим методом не меняется. Правила валидации совпадают с регистрацией, кроме отсутствующего поля `password`.

```json
{"firstName":"Иван","lastName":"Петров","email":"ivan.petrov@example.com"}
```

Ответ — обновлённый объект профиля. Занятый email даёт `409`.

## Каталог

### `GET /catalog/microcategories`

Возвращает все микрокатегории по возрастанию `mcId` (`200`). Не требует авторизации и тела запроса.

```json
{"items":[{"mcId":101,"name":"Ремонт под ключ"},{"mcId":102,"name":"Штукатурные работы"}]}
```

Остальные текущие ID: `103` — плиточные работы, `104` — сантехника, `105` — электрика, `106` — поклейка обоев и малярные работы. Актуальные названия всегда берите из ответа каталога.

## Исходные объявления и анализ

Для `description` требуется непустая строка длиной не более 10 000 символов. `mcId` обязателен и должен соответствовать существующей микрокатегории.

### `POST /source-ads`

Сохраняет исходное объявление пользователя **без запуска анализа** (`201`). Нужен access token.

```json
{"description":"Ремонтируем квартиры под ключ и устанавливаем сантехнику.","mcId":101}
```

Ответ:

```json
{"id":"<source-ad-uuid>","description":"Ремонтируем квартиры под ключ и устанавливаем сантехнику.","mcId":101,"createdAt":"2026-11-14T12:00:00Z"}
```

### `GET /source-ads`

Список исходных объявлений текущего пользователя, сначала новые (`200`). Тела нет. Ответ: `{"items":[<объект объявления>, ...]}`; формат элемента соответствует ответу `POST /source-ads`.

### `GET /source-ads/{id}`

Возвращает одно своё исходное объявление (`200`). Тела нет. Ответ имеет формат объекта объявления выше.

### `GET /source-ads/{id}/analyses`

Список запусков анализа для своего объявления, сначала новые (`200`). Тела нет. Ответ:

```json
{"items":[{"id":"<analysis-uuid>","sourceAdId":"<source-ad-uuid>","status":"completed","stage":"completed","progress":100,"createdAt":"2026-11-14T12:00:00Z","updatedAt":"2026-11-14T12:00:10Z"}]}
```

`modelVersion` присутствует только при ненулевом значении. Сейчас публичного метода запуска анализа для уже созданного `/source-ads/{id}` нет.

### `POST /analyses`

Создаёт исходное объявление и задачу анализа, затем асинхронно отправляет данные в ML-сервис. Нужен access token. Тело такое же, как для `POST /source-ads`:

```json
{"description":"Делаем ремонт квартир под ключ, отдельно разводим трубы и устанавливаем раковины.","mcId":101}
```

Ответ `202 Accepted`:

```json
{"id":"<analysis-uuid>","status":"queued"}
```

`202` означает, что задача поставлена в обработку, а не что ML уже вернул результат. Проверяйте статус через следующий метод.

### `GET /analyses/{id}`

Возвращает состояние своей задачи (`200`). Тела нет. Возможные статусы: `queued`, `processing`, `completed`, `failed`. Пока задача не завершена, `result` отсутствует:

```json
{"id":"<analysis-uuid>","status":"processing"}
```

После успешного завершения `result.drafts` содержит предложения ML, в том числе может быть пустым:

```json
{"id":"<analysis-uuid>","status":"completed","result":{"drafts":[{"mcId":104,"title":"Сантехнические работы","text":"Выполняем разводку труб и установку раковин."}]}}
```

Если генерация текста не выполнялась, у черновика возможны `"title":null` и `"text":null`. Если подходящих услуг нет, ответ содержит `"drafts":[]`. При `failed` смотрите `GET /analyses/{id}/errors`.

### `GET /analyses/{id}/services`

Возвращает обнаруженные услуги своего анализа (`200`), без тела запроса:

```json
{"items":[{"id":"<service-uuid>","mcId":104,"name":"Установка раковин","sourceFragment":"устанавливаем раковины","confidence":0.91,"confirmed":false}]}
```

Поля `sourceFragment` и `confidence` могут отсутствовать, если значение `null`. Текущая интеграция ML сохраняет черновики, но не заполняет таблицу обнаруженных услуг, поэтому сейчас обычно возвращается `{"items":[]}`.

### `GET /analyses/{id}/errors`

Возвращает ошибки обработки своего анализа (`200`), без тела запроса:

```json
{"items":[{"id":"<error-uuid>","stage":"classification","code":"ML_UNAVAILABLE","message":"Нет соединения с ML-сервисом или превышено время ожидания"}]}
```

При недоступном ML ожидается `ML_UNAVAILABLE`; при ошибках HTTP от ML — `ML_SERVICE_ERROR` или `ML_TIMEOUT`; при неправильном ответе — `ML_INVALID_RESPONSE`. Если ошибок нет, `items` пуст.

## Черновики

Черновики появляются только после успешного ответа ML. Они не публикуются автоматически. Все запросы требуют access token.

### `GET /analyses/{id}/drafts`

Возвращает сохранённые черновики своего анализа (`200`), без тела:

```json
{"items":[{"id":"<draft-uuid>","mcId":104,"title":"Сантехнические работы","text":"Выполняем разводку труб.","status":"generated"}]}
```

`title` и `text` могут отсутствовать при `null`. После ручной правки `status` становится `edited`.

### `GET /analyses/{id}/result`

Возвращает черновики своего анализа в кратком формате ML-контракта (`200`), без UUID и статусов:

```json
{"drafts":[{"mcId":104,"title":"Сантехнические работы","text":"Выполняем разводку труб."}]}
```

Пока черновики не сохранены, вернётся `{"drafts":[]}`. Этот путь не различает незавершённый анализ и успешно завершённый анализ без предложений — для этого проверяйте `GET /analyses/{id}`.

### `GET /drafts/{id}`

Возвращает свой черновик (`200`) в формате элемента `GET /analyses/{id}/drafts`. Тела нет.

### `PATCH /drafts/{id}`

Редактирует свой черновик (`200`). Передайте `title` и/или `text`; оба поля должны быть непустыми строками, если указаны. Максимальная длина: `title` — 255, `text` — 10 000 символов.

```json
{"title":"Установка сантехники","text":"Выполняем разводку труб и устанавливаем раковины."}
```

Ответ — обновлённый объект черновика со `status: "edited"`. Пустое тело, `{}` или оба поля `null` дают `400` (`EMPTY_PATCH`); пустая строка для одного из полей также даёт `400`. Через PATCH нельзя очистить поле значением `null`.

## Внутренний контракт с ML

Это **исходящий запрос бэкенда**, а не доступный клиенту endpoint Java API. После `POST /analyses` бэкенд отправляет на `${ML_BASE_URL}/internal/v1/avito/drafts` запрос `POST` с заголовком `X-Request-Id: <analysis-uuid>`:

```json
{"description":"Делаем ремонт квартир под ключ, отдельно устанавливаем сантехнику.","mcId":101}
```

Ожидаемый ответ ML — HTTP `200`:

```json
{"drafts":[{"mcId":104,"title":"Сантехнические работы","text":"Устанавливаем сантехнику."}]}
```

Допустимы `{"drafts":[]}` и `null` для `title`/`text`. Бэкенд отклоняет повторяющиеся и неизвестные `mcId`, исходный `mcId`, а также более пяти черновиков. Сетевые и форматные ошибки переводят анализ в `failed`; подробности доступны в `/analyses/{id}/errors`.

## Быстрая проверка в PowerShell

Каждую строку можно выполнить отдельно после `docker compose up -d --build`:

```powershell
$base = 'http://localhost:8080/api/v1'
Invoke-RestMethod "$base/catalog/microcategories"
$auth = Invoke-RestMethod -Method Post "$base/auth/register" -ContentType 'application/json' -Body '{"firstName":"Иван","lastName":"Иванов","email":"ivan@example.com","password":"password123"}'
$headers = @{ Authorization = "Bearer $($auth.accessToken)" }
$run = Invoke-RestMethod -Method Post "$base/analyses" -Headers $headers -ContentType 'application/json' -Body '{"description":"Ремонт квартир под ключ и установка раковин.","mcId":101}'
Invoke-RestMethod "$base/analyses/$($run.id)" -Headers $headers
Invoke-RestMethod "$base/analyses/$($run.id)/errors" -Headers $headers
```

При повторной проверке используйте `POST /auth/login`, поскольку второй раз зарегистрировать тот же email нельзя. Без работающего ML задача перейдёт в `failed`, но этот сценарий проверяет регистрацию, создание задачи, асинхронный вызов и сохранение ошибки.
